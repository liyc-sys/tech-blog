Some of the best technical posts start from a bug that was annoying enough to
investigate properly.

## Start with the symptom, not the stack

The opening paragraph should usually describe a visible failure:

- latency spikes after a deployment
- a retrieval pipeline getting worse as the context window grew
- a build step that suddenly became flaky in CI

This is better than opening with architecture diagrams or tool names. It gives
the reader a reason to care.

## Capture the observation that changed your direction

Most debugging stories become interesting at the moment when one observation
invalidates the easy explanation.

Examples:

- CPU was fine, but memory churn exploded
- recall dropped only on long-tail queries
- the issue reproduced only on cold runners

That pivot is often the most important sentence in the article because it shows
how you updated your mental model.

## Write down the alternatives you considered

Even if you only tried one real fix, document the alternatives you ruled out.

For example:

1. Increase hardware and accept the cost.
2. Cache more aggressively and accept staleness risk.
3. Change the algorithm and preserve correctness.

The chosen fix matters, but the discarded options are what reveal your tradeoff
thinking.

## Keep the implementation section short

Readers need enough detail to trust the result, not every line of the patch.

Prefer:

```text
We moved reranking behind a coarse filter, reduced candidate fan-out, and added
per-stage timing so regressions could be attributed precisely.
```

Over:

```text
First we changed file A, then file B, then updated the YAML, then edited the
shell script...
```

## End with evidence

Close with the smallest set of numbers that proves the point:

- p95 latency
- throughput
- cost per request
- evaluation accuracy
- failure rate

If the numbers are mixed, say so plainly. Balanced outcomes read as more
credible than perfect wins.
