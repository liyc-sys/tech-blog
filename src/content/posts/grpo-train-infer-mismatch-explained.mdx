很多人第一次在简历或者项目复盘里写“基于 `GRPO` 的 `on-policy` 强化学习训练优化”时，默认心里装着一个前提：采样策略和更新策略是同一个模型，所以这件事理应成立。

但只要把问题往工程实现里再推进一步，这个前提就会开始松动。

更尖锐一点地问，真正该回答的问题不是：

- 训练里是不是用了同一套权重

而是：

- 采样发生在什么引擎里
- `logprob` 是在哪套实现里算出来的
- rollout 和梯度更新是否真的对应同一个策略分布
- 如果采样用的是 `vLLM` 或 `SGLang`，训练用的是 `FSDP` 或 `Megatron`，这两边对同一条 token 序列的概率计算是否完全一致

问题一旦问到这里，结论其实已经很明确了：**工业界大规模 `GRPO` 基本做不到“严格意义上的真 on-policy”。**

原因并不神秘。不是大家不想统一，而是：

- 训练框架和推理框架的优化目标根本不同
- 数值实现天然存在差异
- 这些差异在 `Dense` 模型里往往还算温和
- 到了 `MoE` 模型里会被路由机制显著放大

这篇文章做的事很直接：把“训推不一致”这件事从工程现实、数值机制到主流解法系统拆开。内容重点包括：

- 为什么工业界几乎必然采用双引擎架构
- 什么叫训练-推理不一致，它怎么被量化
- 为什么 `MoE` 比 `Dense` 更容易在 RL 阶段出问题
- `FP16`、`Routing Replay`、`GSPO` 分别在修什么
- 当物理不一致无法彻底消除时，还能打哪些工程补丁

## 先说结论：工业界不是“不想统一”，而是根本没法用一套引擎同时做到训练和推理最优

很多讨论会把问题说成“为什么不用同一个框架做 rollout 和更新”，但这其实把事情说轻了。

更准确的说法是：**大模型训练和大模型生成的硬件优化目标本来就冲突。**

训练阶段需要的是：

- 反向传播
- 梯度计算
- 参数同步
- 大显存调度
- 以吞吐为导向的张量并行、数据并行和分片策略

这一类需求对应的典型系统是：

- `Megatron`
- `FSDP`

它们的任务，是把参数和激活拆到多张卡上，让训练能算得动、梯度能回传、同步开销可控。

推理阶段需要的则是另一套东西：

- 高吞吐
- 低延迟
- 动态 batching
- 高效的 KV cache 管理
- 面向生成路径的 paged attention 与调度策略

对应的系统通常是：

- `vLLM`
- `SGLang`

这两类框架从设计目标就不在一条线上。训练引擎追求的是“梯度可回传且大规模可扩展”，推理引擎追求的是“同样一张卡能更快吐 token”。这不是简单的代码封装差异，而是底层系统假设不同。

所以工业界几乎都会落到同一个架构选择上：

- 采样用推理引擎
- 更新用训练引擎

也就是常说的**双引擎架构**。

这件事并不是工程妥协里的次优选择，而是目前大模型 RL 里几乎不可回避的现实选择。更关键的是，**哪怕强行塞进同一个框架，也不代表就能得到严格的 on-policy 条件。**

原因在于：

- `generate()` 路径和训练前向传播路径本来就不完全相同
- mask 的处理方式可能不同
- KV cache 的使用方式可能不同
- 自回归生成里的累计舍入误差和训练态前向并不等价

所以从系统层面看，工业界大规模 `GRPO` 的真实前提是：

**主动接受一个小但不可忽略的策略差异，用它换来整个训练系统的可运行、可收敛和可上线。**

而这个“主动接受的小差异”，就是训推不一致。

## 什么叫训推不一致：同样的权重，不一定对应同样的策略

在 `on-policy RL` 里，训练至少可以拆成两个阶段：

1. 用当前策略采样数据
2. 用这些样本更新当前策略

理论上，这两步依赖的是同一个策略分布。

但在大模型工程里，情况会变成：

- 样本由推理引擎生成
- 梯度由训练引擎计算

即使两边加载的是同一份模型权重，对同一段 token 序列算出来的对数概率也可能不同。于是“采样用的策略”和“更新时假定的策略”之间，就出现了一个细小但真实存在的偏移。

这就是这里说的**训练-推理不一致**。

为了量化这种差异，可以用文中提到的 `K3 KL` 散度近似衡量训练策略和推理策略之间的偏离：

```text
D_KL(pi_train(theta) || pi_infer(theta))
≈ 1 / |T| * Σ_t [ pi_train(t) / pi_infer(t) - 1 - log(pi_train(t) / pi_infer(t)) ]
```

从文中引用的数据看：

- `Dense` 模型 `Qwen3-8B` 的该值约为 `6.4 × 10^-4`
- `MoE` 模型 `Qwen3-30B-A3B` 的该值约为 `1.535 × 10^-3`

数字表面上都不大，但这并不意味着可以忽略。因为 RL 对策略偏移本来就敏感，而 `MoE` 会进一步把这种偏移放大。

换句话说，**这里的问题不是“数值上差了一点”，而是“这个一点足以让本来假设的 on-policy 更新逐步滑向 off-policy”。**

## 为什么到了 MoE，这个问题会变得明显严重

`Dense` 模型里，训练和推理引擎之间的差异通常主要体现在数值层面，偏差未必会立刻放大成行为层面的剧烈分岔。

但 `MoE` 不一样。`MoE` 把一层网络拆成多个专家，再通过路由器动态选择 `Top-K` 专家参与计算。于是原本“很小的数值扰动”，会被路由机制变成“完全不同的计算路径”。

这里至少有三层放大效应。

### 第一层：路由选择本身就是高敏感决策

在 `MoE` 里，token 会根据路由分数选到若干专家。由于浮点运算不满足结合律，再加上不同硬件和不同算子实现的细微差别，训练引擎和推理引擎即使输入同样的权重和同样的 token，也可能算出略有不同的路由分数。

如果这个差异刚好发生在排序边界附近，那么结果就不是“同一个专家打分略微不同”，而是：

- 训练引擎选了专家 A、B
- 推理引擎选了专家 A、C

一旦 `Top-K` 集合变了，后面的前向路径就已经不是同一条了。

### 第二层：不同专家意味着不同参数子网

`Dense` 模型里，数值扰动通常是在同一套参数里传播；`MoE` 模型里，一旦路由变了，激活的参数块本身都变了。

也就是说，细小的数值差异会迅速演化成：

- 使用不同的专家参数
- 走不同的非线性路径
- 产生显著不同的输出分布

这就是典型的误差放大。

### 第三层：训练态和推理态的路由规则本来就可能不同

为了效率，训练时常见的做法还包括：

- 专家容量限制
- 负载均衡约束
- token 丢弃或重路由

而推理时的 batch 大小、动态 batching 形态、路由触发条件，往往和训练态并不完全一致。于是即便不考虑引擎差异，训练态和推理态也可能天然不一致；再叠加不同系统实现，问题会更明显。

这三层因素加在一起，就很容易出现一个工业界已经相当熟悉的现象：

**`MoE` 模型用 `GRPO` 做 RL 训练，跑到大约一百多步时，奖励突然塌掉。**

这时候只调学习率、clip 或 warmup 往往没什么用，因为真正出问题的不是优化器表面的超参数，而是“你以为自己在做 on-policy 更新，但底层策略假设一开始就被破坏了”。

## 第一类解法：先从数值精度下手，为什么 FP16 反而可能比 BF16 更合适

这部分最反直觉。

在大模型预训练里，`BF16` 基本已经是行业默认选项，因为它和 `FP32` 接近的动态范围能显著降低溢出风险。按经验看，很多人会自然认为 RL 阶段继续用 `BF16` 也是最合理的。

但文中引用的工作给出了一个很不直观的结果：**在 RL 微调阶段，`BF16` 反而可能是放大训推不一致的来源，而 `FP16` 更稳定。**

逻辑并不复杂。到了 RL 微调阶段，模型权重的动态范围通常已经比较稳定，真正稀缺的资源不再是“更大的指数范围”，而是“更细的数值分辨率”。

可以把两者差异压缩成下面这张表：

| 属性 | FP16 | BF16 | 差异分析 |
| --- | --- | --- | --- |
| 指数位 | 5 bits | 8 bits | `BF16` 动态范围更大，但微调阶段往往冗余 |
| 尾数位 | 10 bits | 7 bits | `FP16` 精度更高 |
| 相对精度 | `~0.000977` | `~0.007812` | `FP16` 精度约高 8 倍 |

围绕这张表，原文里的几个结论值得完整保留：

- `BF16` 的尾数只有 7 位，而 `FP16` 有 10 位
- 这意味着 `FP16` 在表示附近数值时更细，舍入误差更小
- 在 RL 阶段，推理引擎和训练引擎由于算子实现不同而产生的误差，会在自回归生成过程中累积
- `FP16` 更高的精度能更好吸收这类误差，从而减少训练策略和推理策略的分歧

文中给出的结论是：**把 RL 阶段的权重和计算精度切到 `FP16`，并配合 `loss scaling` 防止溢出，可以把训推不一致降低约 24 倍。**

这里必须强调一点：这个结论针对的是 **RL 阶段**，并不是说预训练也应该全面回退到 `FP16`。更准确的理解是：

- 预训练继续用 `BF16`
- RL 微调阶段改用 `FP16`

这么做，本质上是在用更高的尾数精度来压低跨引擎数值漂移。

## 第二类解法：Routing Replay，本质是强制训练阶段走和 rollout 一样的专家路径

如果说 `FP16` 修的是数值漂移，那么 `Routing Replay` 修的就是 `MoE` 里最致命的那条链路：**专家路由分叉。**

核心思想可以一句话概括：

**在训练更新时，不再让训练引擎自己重新做一遍路由决策，而是强制它回放 rollout 阶段的专家选择。**

这样做的目标，是尽可能让训练阶段和采样阶段激活同一批专家参数，把 `MoE` 重新拉回到更接近 `Dense` 模型的稳定优化状态。

原文区分了两个版本。

### `R2`：Vanilla Routing Replay

`R2` 复用的是训练引擎旧策略，也就是之前 rollout 时训练侧算出来的专家路由。它主要缓解的是：

- 策略滞后 `policy staleness`
- 因为多步 mini-batch 更新造成的路由偏移

它更像是：**让训练阶段别在同一批数据上不断重算一套越来越偏的专家选择。**

### `R3`：Rollout Routing Replay

`R3` 更激进。它直接记录推理引擎 rollout 时做出的专家路由，并在训练阶段强制重放。

这意味着：

- 训练引擎不仅不再自己重新路由
- 还要直接接受推理引擎当时那套专家选择

所以 `R3` 同时解决两类问题：

- 训练引擎和推理引擎实现不同导致的路由差异
- rollout 与更新之间策略陈旧导致的路由偏移

可以把两者的差别记成一句话：

- `R2` 用的是训练侧旧路由
- `R3` 用的是推理侧 rollout 路由

### R2 和 R3 的取舍，本质是偏差和稳定性的权衡

这部分原文讲得很到位，不能简化成“谁更强”。

因为 Routing Replay 本身并不是零代价的。你一旦强制使用旧路由，就等于把原来由当前目标策略自然决定的专家选择，替换成了一套外部给定的路径。这会引入隐式策略偏差。

所以：

- `R2` 的优势是偏差相对更小，尤其在第一轮 mini-batch 更新时，它和训练旧策略更接近
- `R3` 的优势是稳定性更强，尤其当训练和推理之间已经明显 off-policy 时，它通常更有效

原文给出的判断是：**当 off-policy 程度已经比较高时，`R3` 往往比 `R2` 更好。**

这并不矛盾。偏差更大但更稳定，在很多工程系统里本来就是合理交换。

## 第三类解法：GSPO，关键不是换一个缩写，而是把重要性比率从 token 改到序列

`GSPO` 这条线解决的是另一个更深的问题：**优化权重的粒度必须和奖励的粒度对齐。**

在 `GRPO` 里，重要性采样权重通常是 token 级的。但很多 RL 任务的 reward 实际上是序列级给出的，比如：

- 一道题最终答对还是答错
- 一个 agent 任务最终完成还是失败
- 一条长输出整体是否满足格式和内容要求

如果奖励是序列级，而修正权重却在 token 级逐个做，那么它在 off-policy 条件下就会有两个问题：

- 方差高
- 误差会随序列长度累计

`GSPO` 的思路是把重要性比率提升到**序列级**，再做长度归一化。它的核心不是“换个损失名字”，而是把优化单位和奖励单位重新对齐。

原文保留了两个非常重要的经验结论：

- 相比 `GRPO`，`GSPO` 的训练稳定性明显更好
- 即使不配合 Routing Replay，`GSPO` 也能吸收掉一部分训推不一致

文中的实验设定是：

- 模型：`Qwen3-30B-A3B-SFT`
- `mini_step = 8`
- `max_global_step = 180`

在这个设定下，结论可以概括成：

- `GRPO` 容易在大约 `120` 步附近出现奖励塌陷
- `GSPO` 明显更稳，没有在同一位置崩掉
- 如果再叠加 `R3`，效果还能进一步往上推

这背后的解释也非常值得记住：

**如果不用 Routing Replay，`GRPO` 在 `MoE` 上会快速衰减，而 `GSPO` 即使不做路由回放也能稳定训练，说明序列级重要性比率本身就具备吸收部分训推不一致的能力。**

这不是“GSPO 万能”，而是它在问题定义上更贴近 reward 的真实形态，因此在 off-policy 条件下更稳。

## 当物理不一致无法彻底消除时，还需要一层工程补丁

到这里其实已经能看出一个事实：有些不一致不是你把代码整理一下、把框架统一一下就能完全消掉的。

哪怕代码完全一样，数值也还是可能变化。原因非常基础：

- 浮点加法不满足结合律
- batch 大小一变，底层算子可能触发不同的 split-reduction
- 累加顺序一旦变了，最终结果就可能出现 bit-level 差异

所以工程上还需要再补一层**离线修正和安全阀机制**。

原文列了四类补丁，这里逐条保留。

### `TIS`：Truncated Importance Sampling

做法是裁剪 token 级的概率比率，限制极端 importance ratio 带来的梯度爆炸。它解决的是：

- 某些 token 上训练/推理概率偏差过大
- 由此引出的极端更新

### `MIS`：Masked Importance Sampling

这一步更激进。它相当于引入拒绝采样思想：

- 如果训练概率和推理概率的比率超出阈值
- 直接屏蔽这个 token 或整个序列的梯度贡献

本质上是在说：**这条样本已经偏得太远，不值得继续拿来近似 on-policy 更新。**

### Veto Mechanism

这是 `slime` 框架里提到的一类安全阀。

它的策略是：

- 如果一条序列里任何一个 token 的概率比率进入极端区间
- 就直接否决整条序列，不参与更新

这么做的核心原因是：一旦分母过小，数值会非常不稳定，后面的 importance weight 基本就失去可信度。

### Batch 内自归一化

这一步针对的是另一个问题：采样区域不同会导致有效学习率抖动。

通过在 batch 内强制权重均值约为 `1.0`，可以：

- 降低训练步之间的更新尺度波动
- 在稳定性和偏差之间做一个比较实用的折中

把这些补丁放在一起看，位置很清楚：

- `FP16` 修数值精度
- `Routing Replay` 修专家路径分叉
- `GSPO` 修重要性比率粒度错位
- `TIS/MIS/Veto/自归一化` 修尾部样本和极端梯度

它们不是互相替代关系，而是可以分层叠加。

## 再往外看，还有哪些训练侧和推理侧思路

原文最后还做了一个很有价值的延伸：不把视野局限在 `GRPO + MoE` 的直接修补上，而是把问题放回更大的“训练-推理差异”框架中。

这里可以分成两类。

### 训练侧：尽量降低训练中产生的路由偏差

#### 1. Random Token Selection (`RTS`)

做法是在路由前打乱 token 顺序，避免容量限制优先照顾前缀 token，从而缓解前缀偏置。它解决的是：

- 容量约束下前面 token 更容易占到专家资源
- 由此导致的专家分配不公平

价值在于让训练期的专家利用更均衡，收敛更稳。

参考：

- [RTS 论文](https://arxiv.org/abs/2109.10465)

#### 2. Aggregation of Experts (`AoE`)

这类方法会把专家和门控矩阵做合并，并利用早期 checkpoint 初始化合并结果，目的是：

- 稳定专家表示
- 让继续训练、微调和部署切换更平滑

它更像是一类结构整理与迁移稳定化方案。

参考：

- [AoE 论文](https://arxiv.org/html/2111.15365v4)

#### 3. Auxiliary Load-Balancing Losses

这是更常见的一类办法，通过辅助损失强行推动专家均匀利用，避免训练期专家崩塌。

但它的代价也很明确：

- 训练时专家使用更均匀
- 推理时依然偏稀疏

这样会制造新的分布错位，因此不是没有副作用。

参考：

- [Auxiliary Load-Balancing 相关论文](https://arxiv.org/pdf/2502.17187.pdf)

### 推理侧：尽量缩小部署时和训练假设之间的差距

#### 1. Expert Pruning

按照验证集上的激活频率剪掉低利用率专家，再对剩余专家做微调，以获得：

- 更低推理成本
- 接近原来的精度

参考：

- [Expert Pruning 相关论文](https://arxiv.org/abs/2109.10465)

#### 2. Task-Level Routing

按句子级或任务级分配专家子网，让同任务样本共享一套更粗粒度的路由。这样可以：

- 降低显存与通信开销
- 提升推理吞吐

参考：

- [Task-Level Routing 论文](https://arxiv.org/abs/2110.03742)

#### 3. Matryoshka MoE

训练时允许专家数量可变，让模型学到从粗到细的层级专家排序；推理时再根据算力预算灵活启用不同数量的专家。

它解决的是：

- 不同部署预算下的弹性伸缩
- 速度和精度之间更平滑的折中

参考：

- [Matryoshka MoE 论文](https://arxiv.org/pdf/2509.26520)

#### 4. Capacity-Aware Inference

为每个专家设置最大容量，过载 token 进行重路由或丢弃，用来抑制滞后效应，提升推理速度。

原文给出的结论是：

- 推理速度大约可以提升 `1.9×`
- 精度几乎没有明显损伤

参考：

- [Capacity-Aware Inference 论文](https://arxiv.org/pdf/2503.05066)

## 真正值得记住的，不是某个 patch 名字，而是问题结构

把整篇内容压缩成几句最核心的话，大概是这样：

- 工业界 `GRPO` 难以做到严格 on-policy，不是因为实现粗糙，而是因为双引擎架构几乎不可避免。
- 同样的权重并不自动意味着同样的策略分布；训练引擎和推理引擎的数值差异会真实存在。
- `Dense` 模型里这种差异可能只是小扰动，`MoE` 会通过专家路由把它迅速放大成计算路径分叉。
- `FP16`、`Routing Replay`、`GSPO` 分别对应数值精度、专家路径一致性、重要性比率粒度这三条主修复线。
- 当这些手段仍然不够时，还需要 `TIS`、`MIS`、Veto 和自归一化去兜底。

如果把这件事再说得更工程一点，那就是：

**工业界 RL 训练面对的不是“如何把理论 on-policy 原样搬进系统”，而是“在承认小幅 off-policy 现实存在的前提下，怎样把它控制到模型还能稳定优化的程度”。**

这也是为什么现在真正有价值的工作，越来越少是在口头上强调“我们是 on-policy”，而是开始认真回答下面这些更硬的问题：

- 偏离到底有多大
- 偏离首先出现在哪一层
- 哪一类模型最容易被放大
- 应该在数值、路由、损失定义还是样本筛选上修

这些问题，才是工业界 `GRPO` 能不能跑稳的真正分水岭。
