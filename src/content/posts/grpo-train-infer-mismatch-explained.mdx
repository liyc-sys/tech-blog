前几天有位同学说，他在面试里踩到了一个很典型的坑。

他在简历上写的是：“基于 `GRPO` 的 on-policy 强化学习训练优化”。

面试官先问了一句：“既然你说是 on-policy，那采样时的策略和更新时的策略，能保证完全一致吗？”

他回答说：“能，我们用的是同一套权重。”

面试官接着追问：“权重是一套没错，但采样跑在 `vLLM` 上，梯度更新跑在 `FSDP` 上，这两套框架对同一段序列算出来的 `logprob` 真能完全一样吗？”

他一下就卡住了。

对方又换了个问法：“那为什么工业界几乎没人把训练和推理放进同一套框架里？”

这才是问题真正的核心。

## 为什么工业界必须用双引擎架构？

并不是大家不想把训练和推理统一在一套框架里，而是大模型训练和大模型生成的硬件优化目标从根上就不一致。

- 训练侧需要的是反向传播、梯度计算、大显存占用和参数同步。像 `Megatron`、`FSDP` 这样的系统，就是围绕这套需求设计的。它们的任务是把参数和状态拆到多张卡上，让梯度能算、同步能做、显存能扛住。
- 推理侧需要的则是高吞吐、低延迟、`PagedAttention` 和动态 batching。`vLLM`、`SGLang` 这一类系统，是围绕 token 生成路径去优化的，重点是把 `KV Cache` 的管理效率尽可能压榨到极致。

目前并没有哪套框架能把这两种目标同时做到最优。更关键的是，即便硬把训练和推理塞进同一个框架，也依旧做不到严格意义上的 on-policy。因为 `generate()` 路径和训练态前向在 `mask` 处理、`KV cache` 使用乃至数值累计方式上，本来就可能存在实现差异，这不是简单统一封装就能抹平的。

所以工业界用 `GRPO` 跑大规模 RL 时，几乎都会采用**双引擎架构**：

- 用推理引擎负责采样
- 用训练引擎负责更新

系统层面主动接受一小部分策略偏差，换来的是训练可运行、可收敛、可上线。这不是偶然，而是工程现实决定的结果。

而这部分小但真实存在的偏差，就是本文要讲的**训推不一致**。

## 什么是训推不一致

`on-policy RL` 的训练过程，可以粗略拆成两个阶段：

1. 先用当前策略采样
2. 再用采样出来的数据更新当前策略

所谓训练-推理不一致，说的是在大模型强化学习里，负责生成样本的**推理引擎**，和负责计算梯度的**训练引擎**之间，存在数值上的偏差。

这意味着：即便两边加载的是同一套模型权重，对完全相同的一段 token 序列，算出来的对数概率也可能不同。

这种偏差在 `Dense` 模型里通常比较小，但到了 `MoE` 模型里，会被明显放大。

为了量化这种不一致，可以引入 `K3 KL` 散度：

```text
D_KL(pi_train(theta) || pi_infer(theta))
≈ 1 / |T| * Σ_t [ pi_train(theta)(t) / pi_infer(theta)(t) - 1
                  - log(pi_train(theta)(t) / pi_infer(theta)(t)) ]
```

以文中给出的数据为例：

- 在 `Dense` 模型 `Qwen3-8B` 上，这个值约为 `6.4 × 10^-4`
- 在 `MoE` 模型 `Qwen3-30B-A3B` 上，这个值约为 `1.535 × 10^-3`

表面上看，这两个值都不算大。但问题不在“它是不是肉眼可见的大”，而在于：**这点偏差足以让 RL 更新从理论上的 on-policy，滑向现实里的 off-policy。**

*图 1：强化学习过程中，训练框架与推理框架之间的数值差异会让系统偏离严格的 on-policy 状态。*

## 为什么 MoE 模型不一致性更严重

`MoE` 模型之所以对这类偏差更敏感，根本原因在于它的**专家路由机制**。

- 第一层问题是路由选择本身就带有蝴蝶效应。`MoE` 会基于路由分数动态选出 `Top-K` 专家。由于浮点运算不满足结合律，再加上硬件和算子实现差异，训练引擎和推理引擎产生的微小数值波动，就可能把某个 token 从一组专家切到另一组专家。
- 第二层问题是误差会被迅速放大。一旦路由结果不同，后续激活的就是另一套参数子网，最终输出的概率分布自然可能出现明显分岔。
- 第三层问题是训练态和推理态的策略本来就不完全一致。训练时为了效率，可能会限制专家容量，也可能会加负载均衡，让部分 token 被丢弃或重新路由。推理时的 batch 组织方式和路由动态又往往不同，这会进一步加重差异。

这三层因素叠加之后，就会出现一个很典型的工程现象：

**`MoE` 模型用 `GRPO` 做 RL 训练时，跑到大约 120 步附近，训练奖励突然崩塌。**

这时候无论继续调学习率还是调 `clip`，通常都救不回来。因为真正的问题不是超参数没调好，而是 on-policy 的底层假设从一开始就已经被破坏了。

### 解法一：FP16 替换 BF16

> 参考论文：[https://arxiv.org/pdf/2510.26788](https://arxiv.org/pdf/2510.26788)

在大模型预训练里，`BF16` 几乎已经成了默认配置，因为它拥有接近 `FP32` 的动态范围。

但在 RL 阶段，这篇工作给出了一个很反直觉的结论：**导致数值漂移更严重的反而可能是 `BF16`，而 `FP16` 更稳定。**

原因在于，到了 RL 微调阶段，模型权重的动态范围通常已经比较稳定，不再像预训练那样极度依赖更大的指数范围。这时更稀缺的东西其实是**数值精度**。

| 属性 | FP16 | BF16 | 差异分析 |
| --- | --- | --- | --- |
| 指数位 (Exponent) | 5 bits | 8 bits | `BF16` 动态范围更大，但在微调阶段往往冗余 |
| 尾数位 (Mantissa) | 10 bits | 7 bits | `FP16` 精度更高 |
| 相对精度 (Next Representable) | ~0.000977 | ~0.007812 | `FP16` 精度约高 8 倍 |

- 从尾数位看，`BF16` 只有 7 位，`FP16` 则有 10 位，这意味着 `FP16` 的数值精度大约高 8 倍。
- 更高的精度可以更好地吸收推理引擎和训练引擎之间因为算子实现差异带来的舍入误差，避免这些误差在自回归生成过程中不断积累。
- 工程上的做法通常是：**预训练阶段继续用 `BF16`，而 RL 阶段把权重和计算精度切到 `FP16`，同时配合 `Loss Scaling` 防止溢出。**

文中给出的结论是，这么做可以把训推不一致降低约 24 倍。

*图 2：前两图比较训练与推理的 token-level 概率分布，后两图比较 sequence-level 对数概率比率；越偏离黑线，不一致越严重。图中可以看到 FP16 明显优于 BF16。*

### 解法二：路由重放（Routing Replay）

> 参考论文：[https://arxiv.org/pdf/2510.11370](https://arxiv.org/pdf/2510.11370)

这条路线的核心思想很直接：**训练阶段强制回放推理阶段的专家路由决策。**

这么做的目标，是让训练引擎和推理引擎尽可能激活同一组专家参数，从而把 `MoE` 模型重新拉回到更接近 `Dense` 模型的稳定优化状态。

设训练引擎策略为 `pi_train`，推理引擎策略为 `pi_infer`，文中对 token-level 重要性比率做了两种修改。

- `R2`（Vanilla Routing Replay）：在梯度更新时，回放的是训练引擎旧策略在 rollout 时得到的专家路由。它主要针对的是策略滞后 `policy staleness` 带来的路由偏移。

*图 3：`R2` 复用的是训练引擎旧策略在 rollout 阶段得到的专家路由。*

- `R3`（Rollout Routing Replay）：直接记录推理引擎 rollout 时的路由结果，并在训练阶段强制回放。这同时缓解了引擎差异和策略滞后两类问题。

*图 4：`R3` 直接复用推理引擎 rollout 时记录下来的专家路由。*

如果用一句话概括两者区别：

- `R2` 用的是训练侧旧路由
- `R3` 用的是推理侧 rollout 路由

`R3` 等价于把推理引擎当时的专家选择强行应用回训练引擎；`R2` 则是继续沿用训练引擎旧策略那套路由。

*图 5：`R2` 与 `R3` 的效果对比。*

`R2` 和 `R3` 的取舍，本质上是**偏差和稳定性之间的权衡**。

路由回放本身会引入隐式策略偏差。原本目标策略 `pi_theta` 对应的是自然路由下的专家选择；一旦强制回放旧路由，无论是 `R2` 还是 `R3`，实际优化的都不再是完全原生的 `pi_theta`。

`R2` 的好处是，在第一轮 mini-batch 更新时，它对目标策略的干扰更小，因此偏差通常也更小。但当 off-policy 程度已经比较明显时，经验上往往是 **`R3` 更稳，效果也更好。**

*图 6：在 off-policy 程度更高的设定下，`R3` 通常会比 `R2` 表现得更稳定。*

### 解法三：GSPO，重要性比率从 Token 扩展到序列

> 参考论文：[https://arxiv.org/pdf/2507.18071](https://arxiv.org/pdf/2507.18071)

`GSPO` 解决问题的角度又不一样。它抓住的是这样一个事实：

**奖励的粒度通常是序列级的，但 `GRPO` 的重要性采样修正往往发生在 token 级。**

这会带来两个问题：

- token 级 off-policy 修正并不真正对应奖励的发放方式
- 方差会变大，而且会随着序列长度近似线性累积

`GSPO` 的关键改动，是把重要性比率改成**序列级**，同时再做长度归一化。

*图 7：`GSPO` 使用的序列级重要性比率。*

*图 8：`GSPO` 的长度归一化形式。*

文中给出的实验设定是：

- 模型：`Qwen3-30B-A3B-SFT`
- `mini_step = 8`
- `max_global_step = 180`

实验结果显示：

*图 9：和 `GRPO` 相比，`GSPO` 的训练稳定性更好，没有在 120 步附近崩溃；再叠加 `R3` 后效果还能继续提升。*

更关键的是，论文还给出了一个非常重要的观察：

*图 10：如果不使用 Routing Replay，`GRPO` 在 `MoE` 上的奖励会快速衰减；而 `GSPO` 即使不配合路由回放，也能维持稳定训练。*

这说明一件事：**序列级重要性比率本身就能吸收掉一部分训推不一致。**

换句话说，`GSPO` 的价值不只是“换一种损失定义”，而是它把优化单元重新对齐到了 reward 的真实粒度。

## 工程补丁：当物理不一致无法彻底消除时

即便训练和推理路径的代码写成一样，数值也依旧可能发生变化。根本原因很朴素：

- 浮点加法不满足结合律
- 一旦 batch size 变化，底层算子就可能触发不同的 split-reduction
- 累加顺序一变，最终结果就会出现 bit-level 差异

既然这类物理不一致很难完全消除，那么工程上就只能再叠一层数学修正。

- `TIS`（Truncated Importance Sampling）：通过裁剪 token 级概率比率，限制极端重要性权重带来的梯度爆炸。
- `MIS`（Masked Importance Sampling）：引入一种拒绝采样式的屏蔽机制。当训练和推理的概率比率超过预设阈值时，直接丢弃对应 token 或整条序列的梯度贡献。
- Veto Mechanism：`slime` 框架里的一类安全阀。如果一条序列里任意一个 token 的概率比率进入极端区间，就直接否决整条序列，因为分母过小会带来严重的数值不稳定。
- 自归一化（Batch Normalization）：在 batch 内强制权重均值回到 `1.0`，用来抵消采样区域不同带来的有效学习率抖动，让优化过程更稳，同时尽量保持低偏差。

这四类补丁可以组合使用，本质上都是在 `GSPO + R3 + FP16` 之外，再给系统补上一层兜底机制。

## 延伸：还有哪些思路

> 参考：[https://www.emergentmind.com/topics/training-inference-discrepancies-in-moe-models](https://www.emergentmind.com/topics/training-inference-discrepancies-in-moe-models)

### 训练侧：正则化方法

#### 1. Random Token Selection (RTS)

- 在路由前先打乱 token 顺序，避免容量限制优先照顾前缀 token，缓解前缀偏置，让专家分配更公平，训练收敛更稳定。
- 链接：[https://arxiv.org/abs/2109.10465](https://arxiv.org/abs/2109.10465)

#### 2. Aggregation of Experts (AoE)

- 将专家和门控矩阵做合并，并使用早期 checkpoint 初始化合并结果，借此稳定专家表示，方便后续继续训练、微调和推理迁移。
- 链接：[https://arxiv.org/html/2111.15365v4](https://arxiv.org/html/2111.15365v4)

#### 3. Auxiliary Load-Balancing Losses

- 通过辅助损失强制专家使用更均匀，避免训练阶段出现专家崩塌。
- 但副作用也很明显：训练时更均匀，推理时仍然偏稀疏，训练分布和推理分布之间反而可能形成新的错位。
- 链接：[https://arxiv.org/pdf/2502.17187.pdf](https://arxiv.org/pdf/2502.17187.pdf)

### 推理侧：缩小训练–推理差异

#### 1. Expert Pruning

- 按验证集中的激活频率剪掉低利用率专家，再对剩余专家做微调，可以显著降低推理开销，同时几乎不损失精度。
- 链接：[https://arxiv.org/abs/2109.10465](https://arxiv.org/abs/2109.10465)

#### 2. Task-Level Routing

- 按句子或任务做更粗粒度的专家分配，让同任务样本共享路由结构，降低显存和通信开销，提升推理吞吐。
- 链接：[https://arxiv.org/abs/2110.03742](https://arxiv.org/abs/2110.03742)

#### 3. Matryoshka MoE

- 训练时允许专家数量可变，让模型学到由粗到细的层级排序；推理时再根据算力预算灵活选择专家数，在速度和精度之间做弹性折中。
- 链接：[https://arxiv.org/pdf/2509.26520](https://arxiv.org/pdf/2509.26520)

#### 4. Capacity-Aware Inference

- 为每个专家设置最大容量，超过容量的 token 做重路由或丢弃，以此缓解滞后效应。
- 文中给出的结果是，推理速度可提升约 `1.9×`，同时精度几乎不受影响。
- 链接：[https://arxiv.org/pdf/2503.05066](https://arxiv.org/pdf/2503.05066)
