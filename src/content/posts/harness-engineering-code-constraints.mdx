真正把 coding agent 放进生产型工程环境后，一个很快会暴露出来的问题是：`prompt` 本身并不是足够强的约束机制。它能表达意图，却很难长期稳定地约束结构；它能提醒模型“最好这样写”，却不能保证下周、下个月、下一千个 PR 里仍然这样写。

OpenAI 在博客 [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/) 里讲得很直接。他们在一个完全由 Codex 产出代码的仓库里，逐步形成了一套不是“靠人盯着看”的工程方法，而是“把规则编码进仓库本身”的方法。文章里最值得反复咀嚼的部分，不是 agent 能写多少代码，而是当 agent 成为主力执行者后，工程约束应该放在哪里。

这篇文章就只围绕这一点展开：固定格式约束、结构化约束、仓库级护栏，到底该怎么理解，为什么它们在 agent-first 环境里会从“锦上添花”变成“基础设施”。

## Prompt 不是护栏，代码才是护栏

源文反复强调一个变化：工程师的主要工作不再是亲手写每一行代码，而是设计环境、描述目标、搭建反馈回路，让 agent 能持续做出可靠的工作。

这句话表面上像角色变化，实质上是在重新定义约束的载体。

在人写代码为主的团队里，很多规则可以依赖隐性共识维持：

- 某一层不能直接依赖另一层
- 数据边界必须校验
- 日志必须结构化
- schema 命名要统一
- 文档要更新到位
- UI 性能和启动时延不能突破某个阈值

这些规则即使没有完全写死在机器里，熟悉系统的人也可能靠 code review、口头提醒和经验把它们维护住。

但在 agent-first 环境里，这种默认前提会迅速失效。原因很简单：agent 的产出吞吐远高于人的注意力吞吐。只要规则还停留在“最好这样做”“记得不要那样做”这一层，它迟早会被高频生成和局部 pattern matching 冲垮。

所以源文的真正立场不是“prompt 很重要”，而是：**prompt 用来表达任务，代码化约束用来定义边界。**

也正因为如此，OpenAI 在文章里不断把“约束”从自然语言提升为可以被工具链执行的对象：

- 用文档目录和索引定义知识结构
- 用 lint 和 CI 检查知识库是否过期、交叉链接是否完整
- 用架构分层和依赖校验限制代码形状
- 用结构测试和定制 lint 固化 taste invariants
- 用日志、指标、trace 和浏览器能力让 agent 直接验证结果
- 用后台清理任务持续清除漂移和劣化模式

这套方法的关键不是“多加几条规范”，而是把规范从建议变成可执行事实。

## 第一层约束：先把仓库变成 agent 看得懂的系统

源文里有一句非常重要的话：**从 agent 的视角看，运行时无法在上下文里接触到的知识，等于不存在。**

这句话直接推导出第一类约束：先不要急着约束生成结果，先约束知识的放置方式。

他们一开始也试过“大而全的 `AGENTS.md`”，后来发现这种方式会稳定失败：

- 单个说明文件太大，会挤占任务本身和相关代码的上下文
- 重要信息太多，最后等于没有重要信息
- 文档会快速腐烂，agent 和人都判断不出哪些规则仍然有效
- 大块文本难以做机械校验，覆盖率、 freshness、交叉引用都无法稳定检查

因此他们把 `AGENTS.md` 降级成一个目录入口，而把真正的知识库拆进结构化的 `docs/` 目录里。设计文档、产品规格、执行计划、技术债、生成式参考资料、领域说明，都被组织成可以索引、可以版本化、可以被 CI 检查的仓库内资产。

这里最值得注意的不是“文档更多了”，而是文档本身也被纳入了 harness。

换句话说，这不是传统意义上的“写好文档”，而是：

- 文档目录结构是固定的
- 入口文档是短的，只负责导航
- 深层文档按主题拆分
- 索引、交叉链接、状态信息可被检查
- 过期文档会被自动发现并发起修复 PR

这已经是一种非常明确的“固定格式约束”了。它约束的不是模型输出 JSON，而是约束“团队知识必须以什么形状存在，才能被 agent 使用”。

从 harness 视角看，这比单次输出格式更关键。因为格式化输出只约束一次响应，而知识结构约束的是每次任务开始前 agent 能看到什么、能理解什么、会忽略什么。

## 第二层约束：把架构边界写死，而不是靠代码评审记忆

源文里最接近你说的“用代码做固定格式约束”的部分，其实不在输出格式，而在架构约束。

文章提到他们把每个业务域拆成固定层级，并对依赖方向做严格校验。文中给出的示意层级大致是：

- `Types`
- `Config`
- `Repo`
- `Service`
- `Runtime`
- `UI`

同时，像认证、连接器、遥测、feature flag 这种横切关注点，不允许随意渗透，而是只能通过一个显式接口层进入。

这套规则的重点有两层。

第一层是**结构固定**。一个业务域不是想怎么长就怎么长，而是默认就生活在一个明确层次里。对 agent 来说，这会极大降低生成时的搜索空间。它不用每次都重新“发明一个中间层”或者“临时绕过 service 直接打到 UI”，因为仓库已经提前告诉它哪些形状是合法的。

第二层是**依赖方向固定**。层和层之间不是“尽量这样依赖”，而是“只能这样依赖”。一旦出现逆向依赖、越层调用或非法边，定制 linter 和结构测试就会报错。

这类约束之所以重要，是因为它解决的是 agent 最容易放大的一类问题：局部正确、全局漂移。

模型非常擅长在局部把问题补上，但如果没有刚性边界，它也很容易为了快速完成当前任务，顺手破坏长期结构，比如：

- 直接跨层读取本不该碰的数据
- 在 UI 层内嵌业务判断
- 用某个 util 偷渡跨域依赖
- 把本该统一建模的逻辑散落到多个入口

人类团队里，这些问题可能靠强 reviewer 慢慢拦；agent 团队里，如果不机械拦截，就会随着吞吐指数级扩散。

所以源文的做法不是教 agent “理解架构”，而是先把架构写成机器能检查的约束，再让 agent 在约束内部自由发挥。

## 第三层约束：边界必须可解析，不能靠猜

源文还提到一个非常关键的原则：**在边界处解析和校验数据形状。**

这个原则表面上只是类型安全，实际上是 agent 工程里的核心护栏。

因为 agent 很容易在“不完全知道数据长什么样”的情况下先写出一条凑合能跑的路径。对人来说，这类代码也常见，但 agent 会把这种做法快速复制到全仓库：先 probe 一下字段，试试有没有，再根据局部观察继续拼代码。

OpenAI 在文中明确反对这种做法。他们要求数据边界必须显式解析，或者依赖已经类型化的 SDK，而不是让系统建立在猜测的 shape 上。库选型本身不重要，重要的是边界不能模糊。

为什么这条规则要升级成代码，而不是停留在 code review 评论里？

因为边界校验不是局部风格问题，而是系统可推理性的前提。只要边界没有被显式化：

- agent 就无法稳定推断输入输出
- 后续改动会建立在脆弱假设上
- 错误会以延迟的方式暴露在更远的调用链上
- 仓库里的 pattern 会越来越像“猜测驱动开发”

这也是源文里所谓 “golden principles” 的典型例子。它们不是“写得优雅一点”的审美建议，而是必须不断被工具重申的生成规则。

## 第四层约束：把 taste 也变成可执行规则

很多团队谈“代码规范”时，只想到 formatter、lint 规则和命名约定。但源文里更有意思的一点，是他们把一部分工程 taste 明确提升成了可执行 invariants。

文中点到的例子包括：

- 结构化日志
- schema 和 type 的命名规范
- 文件大小限制
- 平台相关的可靠性要求

这些约束不一定都是功能正确性的必要条件，但它们决定了仓库会不会在高吞吐生成下变得越来越难维护。

更关键的是，他们不是用通用 lint 规则草草覆盖，而是用了**定制 lint**。原因很现实：只有定制规则，才可以把团队真正关心的约束写进去，也可以把报错信息写成 agent 能立即利用的 remediation instruction。

这点非常值得注意。对 agent 来说，一条好的错误信息不只是告诉它“哪里错了”，还要告诉它“应该改成什么样，去看哪份文档，遵循哪个模式”。

也就是说，在 agent-first 仓库里，lint error 已经不只是给人看的失败提示，而是 feedback loop 的一部分。它本身就是 harness 接口。

这就把“固定格式约束”又往前推进了一步：

- 不只固定产物形状
- 还固定违规后的纠错入口
- 不只告诉 agent 不能做什么
- 还把下一步修复路径显式注入回上下文

## 第五层约束：只约束边界，不微观规定实现

如果只看到上面这些规则，很容易误以为 agent-first 工程一定会走向极端中心化：所有事情都统一规定，所有实现都必须长得一模一样。

但源文明确不是这个立场。

他们强调的是：**集中约束边界，局部实现保留自治。**

例如他们要求在边界解析数据形状，但并不死规定一定要用哪一个库；模型最后偏好 `Zod`，是模型自己的实现选择，不是团队预先写死的唯一答案。类似地，他们严格约束层级和依赖边，却不要求每个 service 函数都遵循完全相同的写法。

这是这篇博客里非常成熟的一点。因为真正能扩展的 harness，从来不是对实现细节过度管控，而是把控制力放在几个最影响系统长期演化的地方：

- 边界是否清楚
- 依赖是否可预测
- 数据是否可验证
- 文档是否可发现
- 日志和指标是否可查询
- 偏离是否能被自动纠正

只要这些硬边界被编码了，agent 在局部怎么写，反而可以宽松一些。这样才能同时保住吞吐和可维护性。

## 第六层约束：让 UI、日志和指标都进入 harness

源文里还有一类很容易被忽略，但其实非常关键的“代码化约束”：不是直接约束代码形状，而是约束验证通道。

他们做了两件事：

- 让应用能按 `git worktree` 启动，agent 可以在每个变更上驱动一份隔离实例
- 把浏览器能力和本地可观测性栈都接进 agent 运行时，让 agent 能读 DOM、截图、导航、查日志、查指标、查 trace

这样一来，很多原本只能靠人肉验收的要求，就可以被提升成 agent 可执行的验收条件，比如：

- 某条用户路径不能报前端错误
- 某个服务启动要低于特定时延
- 关键链路里的 span 不能超过某个阈值

这和普通意义上的测试自动化不完全一样。测试自动化通常是人先写好断言，再让机器执行；这里更进一步，agent 自己可以利用环境中的可见信号去复现问题、验证修复、再次观测，再继续迭代。

从 harness 角度看，这其实也是约束。因为“验证能力是否进入仓库环境”本身会决定 agent 能否对结果负责。如果它只能生成代码，却看不到运行后的 UI、日志和指标，那很多约束最终仍然得靠人兜底。

所以源文的思路不是单纯加更多检查，而是把应用可见性本身产品化，做成 agent 的原生工作台。

## 第七层约束：高吞吐下，清理机制必须常驻

源文里另一个很实在的观察是：即使前面所有约束都存在，agent 仍然会复制仓库里已有的次优模式。只要代码库里已经有不均匀、不整洁、临时性的写法，模型就会把它们继续繁殖出去。

这意味着约束不是一次性工作，而必须带有“垃圾回收”机制。

他们的做法是把一些 golden principles 直接编码进仓库，然后定期跑后台 Codex 任务：

- 扫描偏离模式
- 更新质量评分
- 提交小型重构 PR
- 用极短 review 周期自动合并多数修复

这个思路特别像运行时里的垃圾回收器。重点不在“偶尔做一次大扫除”，而在于持续、低成本、高频率地把偏移拉回主轨道。

这对 agent-first 仓库几乎是必需的。因为吞吐一旦上来，技术债就不再是线性增长，而会借由模式复制迅速扩散。靠人每周集中半天清理，最后只会变成永远追不上。

所以更合理的方式是：

- 把你真正介意的模式抽象成规则
- 把规则变成可扫描条件
- 把扫描结果直接变成修复 PR
- 把“口味”从一次性 review 意见变成持续执行的系统行为

这比“写一篇编码规范文档”高出了整整一个层级。

## 这套方法背后的核心思想，其实是 legibility

如果把源文关于代码化约束的内容收束成一句话，我会概括成：**不是先问 agent 能不能写，而是先问仓库是不是足够可读、可查、可约束、可纠偏。**

源文里反复出现的词是 `legibility`。它既包括代码可读，也包括架构可读、知识可读、运行状态可读、错误可读、修复路径可读。

一旦接受这个框架，很多工程决策都会重新排序：

- 为什么知识要进仓库而不是散在 Slack 和 Google Docs
- 为什么要有固定文档结构和入口索引
- 为什么要限制分层和依赖方向
- 为什么边界必须有 schema 或显式解析
- 为什么 lint 规则要定制化
- 为什么错误信息本身要能教 agent 修复
- 为什么 observability 也要接进 agent runtime
- 为什么后台清理任务要长期存在

这些看起来分散的实践，本质上都在服务同一个目标：让 agent 在仓库内部就能看清系统，并且一旦偏离就能被机器拽回来。

## 可以直接落地的实践清单

如果把这篇博客里的思路转成更可执行的工程清单，我会优先做下面几类事情。

### 1. 把“知识组织方式”也纳入 harness

- 保留一个很短的 `AGENTS.md` 或入口文档，只负责导航
- 把真正的规范、设计、产品约束、执行计划放进版本化目录
- 为文档建立索引、交叉链接和状态字段
- 用 CI 检查缺失、过期和断链

### 2. 给每个业务域设固定层次和允许依赖边

- 不要求所有目录长得一样，但要求核心域遵循相同的层次模型
- 用定制 lint 或结构测试检查逆向依赖、越层调用和跨域偷渡
- 把横切关注点收束到少数显式入口

### 3. 在边界处强制显式校验

- API 输入输出、外部服务返回值、文件内容、配置项都不要“先猜再写”
- 用 schema、typed SDK 或显式解析函数把边界收紧
- 把“不得依赖 guessed shape”升级成持续扫描规则

### 4. 把团队真正介意的 taste 写成规则

- 结构化日志
- 命名约定
- 文件大小和模块复杂度上限
- 可靠性、性能和平台兼容性红线

### 5. 让错误信息承担教学职责

- lint 报错不要只说失败
- 直接给出修复方向、文档入口和推荐模式
- 让失败信息天然适合作为 agent 下一轮上下文

### 6. 把验证环境也产品化

- 让 agent 能自己启动、驱动、观察应用
- 把 DOM、截图、日志、指标、trace 暴露给它
- 尽量把“验收要求”改写成可观察、可重复、可自动判定的信号

### 7. 给仓库配一个持续垃圾回收器

- 周期性扫描漂移模式
- 自动提交小型修复 PR
- 高频、低成本地还债，而不是低频、大爆炸式整治

## 最后收束一下

OpenAI 这篇文章真正有价值的地方，不是“他们让 agent 写了很多代码”，而是他们展示了一种更接近未来的工程观：当代码生成变得便宜以后，真正稀缺的不是实现能力，而是边界设计、反馈设计和约束设计。

从这个角度看，“固定格式约束”不能只理解成让模型输出某个 JSON。更重要的是把仓库的知识结构、架构形状、依赖方向、边界校验、日志规范、性能红线和清理机制都编码进工具链里。这样 agent 才不是在一个模糊环境里碰运气，而是在一个高约束、可验证、可恢复的 harness 里稳定工作。

这也许才是 harness engineering 最值得学的部分：**把人的工程判断，从一次次 review 评论，迁移成会持续生效的代码和系统。**
